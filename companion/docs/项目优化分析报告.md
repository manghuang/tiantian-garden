# 2DPic-3Dmodule 项目优化分析报告

## 1. 审查范围与结论

- 审查日期：2026-09-19
- 范围：根目录的 3D 模型生成/导出链路、`companion` 浏览器应用、Node 服务、Cloudflare Worker/Durable Object、语音服务、测试与交付文档。
- 约束：本次只读分析；没有修改现有源码、配置、模型、音频或删除任何用户文件。本文件是唯一新增的分析文档。

总体判断：项目已经具备“受控演示原型”的完整闭环，自动化测试覆盖也比较扎实；但当前最重要的问题不是再增加功能，而是把真实语音/浏览器/移动设备验收、儿童使用安全边界、观测与发布一致性补齐。当前适合成年人和受控环境体验，不建议仅凭现有自动测试开启真实儿童生产使用。

优先级顺序建议为：

1. 儿童安全与真实端到端验收；
2. 语音首音延迟、取消恢复和费用控制；
3. 模型/音频资源和移动端持续性能；
4. Cloudflare 控制层的扩展性与可观测性；
5. 仓库交付一致性、CI 和代码拆分。

## 3. 必须优先处理的事项（P0）

### 3.1 儿童使用开关不能等同于儿童安全能力

现有实现已经正确地默认关闭 `CHILD_USE_ENABLED`，并在界面中提示“共享口令不是家长身份验证”。这是正确的保守策略，但它仍然只是一个部署开关，不是年龄核验、有效家长同意、数据保留配置或内容安全系统。相关边界在 [`companion/README.md`](../README.md:71)、[`companion/server/app.js`](../server/app.js:86) 和 [`companion/cloudflare/control.js`](../cloudflare/control.js:145) 中都有体现。

上线前建议把儿童模式改成“多条件闸门”：

- 服务方数据保留、区域、账号权限和组织责任人确认完成后才能启用；
- 家长同意应有可验证的主体、版本、时间和撤回路径，而不是只接受浏览器传来的 `consent: true`；
- 增加年龄适配的内容策略、危险内容升级路径、举报/人工处置入口和审计记录；
- 输入、模型输出、工具动作和语音播放都要有明确的安全边界；内容检查服务不可用时应默认停止或转入有限本地内容，而不是继续放行；
- 继续坚持不保存录音和对话正文；如果增加指标，只记录脱敏的状态、时延、错误类别和字节数。

### 3.2 实时语音目前是“输出审核”，不是完整的输入安全闸门

`ReviewedRelay` 会缓存完整回答，审核通过后才发送字幕、动作和音频；但其注释已经明确说明输入音频会直接进入 Realtime，尚未经过输入审核。DeepSeek 模式只有配置 `OPENAI_API_KEY` 时才调用文本审核；没有该密钥时显示为 `local-rules`，本地关键词规则不应被当作儿童内容安全的等价替代。见 [`companion/shared/reviewed-relay.js`](../shared/reviewed-relay.js:4)、[`companion/shared/moderation.js`](../shared/moderation.js:1) 和 [`companion/cloudflare/control.js`](../cloudflare/control.js:103)。

建议根据目标安全等级选择一种明确架构：

- 严格模式：语音先 ASR，再输入审核，再生成结构化回复，再输出审核，最后 TTS；
- 低延迟模式：只允许成年人测试，并在界面、部署和文档中明确“不是儿童生产安全模式”；
- 所有模式都限制工具动作、回答长度、话题范围、会话时长和单用户成本。

### 3.3 必须完成真实端到端验收，而不是继续扩大模拟测试

当前 140 项自动测试通过是很好的工程基线，但仍主要验证协议、边界、模拟上游和本地文件。README 和验收文档也明确写着真实麦克风、浏览器播放、移动设备长期性能、真实音色相似度、Alarm 和回滚仍有待验证。

建议建立一份可重复的 staging 验收矩阵，至少包含：

- Chrome/Edge 桌面、Android Chrome、iOS Safari；
- 无麦克风、拒绝权限、切后台、锁屏、耳机/外放、弱网、断网重连；
- DeepSeek + Cloudflare ASR + 各种 TTS、OpenAI Realtime、GPU 桥接断开/重连；
- 首次模型下载、缓存命中、WebGL context lost、低电量和长时间运行；
- 语音打断、连续 10–20 轮、到时挂断、退出登录、Worker 重启、Durable Object Alarm；
- 真实账号的限额、余额不足、429、上游 5xx 和超时。

每次验收保存版本 ID、配置摘要、设备/浏览器、首音延迟、总时延、断线率和结果；不保存音频或儿童对话正文。

## 4. 语音链路优化（P1）

### 4.1 降低首音延迟

当前 DeepSeek 回复使用非流式 JSON；MiniMax 直连请求也明确使用 `stream: false`，并把十六进制音频完整读入内存后再分片。Cloudflare MiniMax 还会先拿完整音频再转码为 24 kHz PCM。相关位置为 [`companion/shared/deepseek.js`](../shared/deepseek.js:15)、[`companion/shared/speech-services.js`](../shared/speech-services.js:171) 和 [`companion/shared/speech-services.js`](../shared/speech-services.js:227)。

建议按风险从低到高优化：

1. 先对回答做句子级上限，例如 1–3 句、每句较短；在不破坏 JSON 结构的前提下，对 TTS 做句段队列；
2. 对固定欢迎语、预设故事和安全兜底回复继续使用预录音或缓存；
3. 供应商支持时使用真正的 TTS 流式响应；不支持时至少把“生成、审核、转码、播放”各阶段打点；
4. GPU 桥接保持预热，并记录排队、推理、转码和网络四段耗时；
5. 不要默认跨供应商自动重试或回退，以免一次用户操作产生两次计费；回退应是显式策略并有预算上限。

建议验收指标：成年人 staging 下首音 p50/p95、打断生效时间、回答完成率、取消后迟到音频丢弃率、每轮估算成本和单会话预算都应可见。具体阈值应按供应商和设备实测后确定，不要直接用本地模拟延迟代替。

### 4.2 统一音频时长上限

系统把 MPEG 输出的 `maxPlayedMs` 固定为 30 秒，但 TTS 字节上限是 1,440,000 bytes；对于 32 kHz、128 kbps MP3，这两者不是同一时长约束。相关代码在 [`companion/shared/deepseek-session.js`](../shared/deepseek-session.js:96) 和 [`companion/shared/speech-services.js`](../shared/speech-services.js:11)。极长回答可能在生成阶段通过、到浏览器解码/排程阶段才失败。

建议以“最大字符数 + 最大音频时长 + 最大字节数”三者中最严格者为准，并在服务端生成前拒绝或截断；客户端播放队列、`played` 校验、Worker 中继和 TTS 适配器使用同一个常量来源。

### 4.3 明确不同 TTS 配置的有效矩阵

`wrangler.jsonc` 同时设置 `DEEPSEEK_TTS=cloudflare-minimax` 和 `TTS_PROVIDER=minimax_direct`，实际选择逻辑会优先落到直连 MiniMax；示例配置和文档又分别展示 Cloudflare 与直连两种默认方式。逻辑本身有测试，但运维人员不容易从配置名判断最终生效的供应商。

建议增加 `npm run config:check` 或等价的配置诊断，输出：

- 实际 ASR、对话、TTS provider；
- 需要的 Secret/AI binding；
- 是否会触发输出审核；
- 是否依赖本机 GPU；
- 当前并发、超时和费用上限。

同时为 Cloudflare、MiniMax 直连、MeloTTS、GPU 和 OpenAI 各保留一份经过验证的最小配置，不再让多个变量组合出隐含优先级。

## 5. 3D 模型与前端性能（P1）

### 5.1 轻量模型仍应继续做真正的移动端 LOD

当前模型优化策略已经保留完整毛束连通性、形态键、混合权重和动画，质量取舍是合理的；但轻量模型仍有约 50.6 万三角面，原始模型约 106 MiB。模型报告写明毛束保留 8%，脚本在 [`companion/scripts/model/optimize-model.js`](../scripts/model/optimize-model.js:30) 和 [`companion/scripts/model/model-lod.js`](../scripts/model/model-lod.js:2)。

当前“省电显示”只是隐藏 Groom 网格并降低像素比，代码和 README 都明确说明不会减少已选模型的下载量和完整内存占用，见 [`companion/src/dog-scene.js`](../src/dog-scene.js:122) 和 [`companion/README.md`](../README.md:98)。

建议提供至少三档交付资产：

- mobile：约 10–20 万三角面，较少毛束和纹理；
- balanced：当前约 50 万三角面的桌面/中端档；
- full：原始高质量制作资产，仅在桌面或明确选择时使用。

选择依据可以是屏幕宽度、设备内存、WebGL 能力和网络状况；省电按钮则只负责运行时降负，不应被误认为下载优化。

### 5.2 启用交付压缩并关注音频资源

当前 GLB 校验报告没有压缩扩展。建议评估：

- Meshopt 或 Draco 几何压缩；
- KTX2/BasisU 纹理压缩；
- 通过实际 Android/iOS 浏览器验证加载和材质质量；
- 76 个 WAV 预录音改为浏览器覆盖足够好的压缩格式，保留必要的兼容回退。

压缩后必须重新验证动画通道、形态键、眼睛贴图、口型、音频播放和缓存行为，不能只比较文件大小。

### 5.3 渲染循环应按可见性和工作状态降频

`DogScene` 当前在构造时持续调用 `renderer.setAnimationLoop`，并一直创建环境光、三盏灯和完整场景；页面隐藏时只是跳过渲染，循环本身仍在运行。见 [`companion/src/dog-scene.js`](../src/dog-scene.js:30)、[`companion/src/dog-scene.js`](../src/dog-scene.js:50) 和 [`companion/src/dog-scene.js`](../src/dog-scene.js:126)。

建议加入：

- `IntersectionObserver`，模型离开视口时暂停；
- 没有动作、说话或相机交互时降低帧率；
- 基于实际 FPS/温度反馈动态调整 DPR，而不是固定 `devicePixelRatio` 上限；
- WebGL context lost 后可恢复或重新加载，而不是只提示刷新；
- 用预览图作为模型下载期间的占位，改善首次体验。

这部分应以持续 5–10 分钟的低端移动设备测试为准，不能只看一次桌面 FPS。

## 6. Cloudflare、Node 服务与可观测性（P1）

### 6.1 单 Durable Object 是当前规模的瓶颈和故障域

Cloudflare 使用固定名称 `garden-control-v1` 的一个 Durable Object，所有登录、会话名额、WebSocket、Alarm 和本机 GPU broker 都经过同一对象；同时 `mutate` 使用 `blockConcurrencyWhile` 并在每次调用后写回完整状态。见 [`companion/cloudflare/control.js`](../cloudflare/control.js:12)、[`companion/cloudflare/control.js`](../cloudflare/control.js:16) 和 [`companion/cloudflare/control.js`](../cloudflare/control.js:37)。文档也明确当前只支持三条并发试用链路。

在当前小规模试用阶段可以保留，但扩展前建议：

- 按用户/租户/区域分片会话对象；
- 把全局预算与单用户会话状态分开；
- 只在写操作或定时清理时进入串行持久化，GET 鉴权尽量使用短期缓存或更轻的读取路径；
- 将本机 GPU broker 与通用控制层分离，避免 GPU 桥接异常影响所有用户；
- 做 3、10、50 并发的压测，观察 DO 延迟、Alarm 延迟和对象替换行为。

### 6.2 未拿到 provider call id 的窗口需要可回收设计

当前文档已经诚实记录：供应商成功创建但应用尚未拿到 call id 的窗口无法可靠回收。建议使用供应商支持的幂等键/客户端请求标识（若接口支持），并增加“创建中操作”记录、超时对账任务、供应商侧预算上限和报警；不要把未知状态简单当成成功或失败。

Node 旧入口则把登录、限流和会话保存在进程内，重启会撤销登录；如果未来运行多实例，必须引入共享会话/限流存储，不能直接横向复制当前部署模板。相关设计在 [`companion/server/access.js`](../server/access.js:25) 和 [`companion/server/app.js`](../server/app.js:18)。

### 6.3 建立最小可用的隐私安全观测

建议打开 Cloudflare 的受控 observability，并补充结构化事件：

- `request_id`、部署版本、provider、阶段、耗时、状态类别；
- WebSocket 建连/关闭原因、会话时长、音频字节数、ASR/TTS/审核成功率；
- 模型下载耗时、加载成功率、FPS 档位、WebGL context loss；
- 供应商 trace id（已有 MiniMax 的安全处理方式可复用），但不记录密钥、正文、音频、完整 SDP 或 Cookie。

健康检查建议拆成 liveness 和 readiness：进程活着不代表模型资源、Durable Object、TTS binding 或 provider 配置可用。当前 `/api/health` 主要返回进程状态和是否配置 OpenAI，见 [`companion/server/app.js`](../server/app.js:44) 和 [`companion/cloudflare/control.js`](../cloudflare/control.js:70)。

另外，Cloudflare Worker 对受保护资源明确设置了 `private, no-store`；Node 的 GLB `sendFile` 路由目前没有同等级的缓存策略，见 [`companion/server/app.js`](../server/app.js:134)。建议统一受保护模型/语音资源的缓存语义，避免登出后仍由浏览器缓存直接复用受保护资源。

## 7. 测试、发布与维护性（P1/P2）

### 7.1 建立 CI 和可重复的发布门禁

仓库当前没有 `.github` 工作流，也没有覆盖率门槛。建议至少加入：

1. Node 22.12 及锁文件安装；
2. `npm test`；
3. Vite production build；
4. 轻量模型校验、Khronos 校验和交付清单哈希检查；
5. Cloudflare dry-run，不执行真实 deploy；
6. 可选的 Playwright/真实浏览器 smoke，至少覆盖登录、模型加载、文字演示、结束和窄屏布局；
7. 生产发布前的人工 staging checklist 和回滚验证。

测试数量不要再硬编码在 README 中，改为 CI 产出或脚本自动生成。本次已将当前版本文档统一为 140 项；历史阶段记录中的旧数字保留为历史证据。

### 7.2 先完成当前目录迁移，再做新功能

本次提交前，工作树中旧的 `companion/CLOUDFLARE.md`、`companion/DEEPSEEK.md`、旧脚本路径等显示为已删除，而新的 `companion/docs/`、`companion/scripts/cloudflare/`、`companion/scripts/model/`、`companion/scripts/voice/` 仍是未跟踪目录。这是一次尚未提交完的目录重组，而不是代码缺陷；在中间状态下容易出现：

- 干净克隆缺少新目录内容；
- 文档链接在不同提交之间断裂；
- 发布包没有包含新脚本或验收记录；
- 审查者误把删除和新增看成两个独立变化。

本次已把迁移、链接更新、测试脚本路径更新和文档计数作为同一提交完成；后续仍应在干净克隆中重新运行启动、构建和测试。

### 7.3 减少协议与 UI 状态机的重复

当前 WebSocket Realtime 经过 `VoiceRelay`、`ReviewedRelay`、`DeepSeekSession`，浏览器又有 `RealtimeProtocol`；它们分别处理事件顺序、动作白名单、打断、工具调用和音频播放状态。现有测试覆盖充分，但规则分散会增加后续供应商切换和安全修复的漏改概率。

建议建立一个共享的事件 schema/状态表：

- 客户端可发送事件；
- 服务端可接收的 provider 事件；
- 可公开给 UI 的事件；
- 每个状态允许的下一事件；
- 每个音频 item 的时长和截断约束。

`main.js` 也同时包含 HTML 模板、状态变量、家长设置、语音确认、活动逻辑和事件绑定，建议拆成 `app-state`、`settings-panel`、`conversation-view`、`session-controller` 和 `accessibility` 五类模块，降低继续加玩法时的回归风险。

## 8. 推荐实施路线

### 阶段 A：发布可信度与安全闸门

- 完成目录迁移并修正文档链接、测试数和当前部署状态；
- 加入 CI、配置诊断和 clean-clone 验证；
- 保持 `CHILD_USE_ENABLED=false`；完成真实账号、麦克风、播放、移动设备和回滚验收；
- 明确输入审核、输出审核、人工升级和数据责任边界；
- 打开隐私安全观测，先只采集元数据。

### 阶段 B：体验和成本

- 统一回答/音频时长上限；
- 句段化 TTS、缓存固定回复、GPU 预热和分阶段延迟指标；
- 交付 mobile/balanced/full 三档模型；
- 评估 Meshopt/Draco、KTX2/BasisU 和压缩音频；
- 完成 5–10 分钟移动设备持续性能测试。

### 阶段 C：规模化和长期维护

- DO 分片、全局预算协调和 provider 会话对账；
- 统一协议 schema 和状态机；
- 拆分前端大模块，补无障碍和真实浏览器回归；
- 建立版本化验收报告和自动生成的交付清单。

## 9. 建议的上线门槛

在允许真实儿童使用前，至少满足以下条件：

- 儿童模式的组织、服务方数据设置、家长同意、年龄适配和风险处置已由责任人确认；
- 真实目标设备完成语音输入、播放、打断、后台、断网、到时和退出测试；
- 输入和输出安全策略、失败关闭行为和人工升级路径经过演练；
- 关键时延、失败率、断线率、资源加载和费用有可查询指标；
- 发布包能从干净克隆复现，测试/校验/构建门禁通过，回滚版本已保留并实际演练；
- 任何“声音与原版一致”的描述都有人工听辨和授权证据，不以转写、声纹或协议通过替代听感与权利确认。
